# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- `README.md` maps the repository, `docs/README.md` indexes the documentation by task, and `docs/REPRODUCTION.md` is the path from a clean checkout to a free end-to-end run. Keep all three current when you add a document or a top-level directory.
- The data root and the credential directory are configuration, not constants: `ARCTIC_QA_DATA_ROOT` and `ARCTIC_QA_CONFIG_DIR`, resolved in `src/arctic_qa/paths.py`. The tests take `ARCTIC_CH2_EVIDENCE_DIR`, `ARCTIC_REAL_CORPUS_DIR`, `ARCTIC_REAL_CORPUS_RUN` and `ARCTIC_ZOTERO_RECEIPTS_DIR`. Never hard-code an absolute path of one machine in `src/` or `tests/`; give it an environment variable whose default keeps the current value.
- Task reports and their measurement files go under `research/<task>/`, never `data/`, and `research/README.md` needs a row for each new directory. The reports keep their historical absolute paths, because they are records.
- Read `docs/CORPUS_VIEWER.md` before you operate the read-only corpus-stage monitor.
- Read `docs/PUBLICATION_EXPORT.md` before you operate the live publication snapshot service.
- Read `docs/SOURCE_SCREENING_PASS.md` before you operate a bounded source pass.
- Read `docs/BENCHMARK_GUARD.md` before you operate the benchmark cost and quota guard or the "Live benchmarking" section of the viewer. The guard pauses one model through the `benchmark-evaluation-model-pause-v1` file and never by stopping a process; it removes only the entries it owns. Its own cross-cycle state lives in `guard-memory.json` in the guard dir: the Codex attribution samples and the pause hysteresis. Never put guard state in the pause file, and never copy a guard dir between runs of different journals. A shared quota window with no per-caller attribution needs a measured share before a rule pauses on it: the Codex projection rule flapped on 2026-09-16 because "the evaluator booked one more call" was taken as proof that the benchmark drove the window.
- Read `docs/ABSTENTION_EVALUATION.md` before you build, dry-run, or run the abstention evaluation. A paid run needs a reviewed private evaluation gate and the construction files that the production ledger already binds; the dry run needs neither.
- A subscription evaluation run (Claude Code, Codex) needs the harness login, a reviewed gate with `--provider`, and a subscription ledger directory. Do not change the Codex config in `abstention_subscription.py` without a captured request: `tools.web_search = false` does not remove web search, only `web_search = "disabled"` does. The evaluation gate binds `config/benchmark-evaluation-subscription-models-v1.json` by hash in the price-config slot, so its absolute binary paths stay as they are; another machine passes `--binary-path` or its own registry file.
- A provider can omit either zero token count. gemini-3.7-flash omitted `candidatesTokenCount` once in three calls on 2026-09-16 and halted the shared ledger. `_omitted_zero_usage_field` accepts both shapes, and `reconcile_omitted_thought_usage` settles either from the saved response. Read section 7 of `research/arctic-abstention-streaming-eval-r1/report.md` before the large Gemini run.
- A usage record missing BOTH token counts must keep raising `provider usage cannot prove zero thinking tokens`. The reviewed chapter 2 continuation of the `answer_agreement` MAX_TOKENS incident matches receipts by that exact string, so a changed message breaks a money-settlement path. `tests/test_ambiguous_continuation.py` is the guard.
- The evaluator's paused-model switch is a documented interface that the benchmark cost guard calls: the `benchmark-evaluation-model-pause-v1` file, the repeatable `--pause-file`, and `--action pause-status`. `docs/BENCHMARK_GUARD.md` holds the guard's half. A paused model's trials stay pending, so read a run's totals through `CostJournal.latest_item_rows`.
- An ambiguous `benchmark_evaluation` request halts the evaluation phase only, through `evaluation_halted` in the ledger. Construction continues under its own ceiling. Never widen that halt back to the whole ledger: one evaluation error stopped the live chapter 3 producer on 2026-09-16.
- Release that charge under its own derived per-item evaluation gate, never the construction gate: `authorize-ambiguous-continuation` takes the evaluation trio and picks the gate and the run-id field (`authorized_run_id`, not `authorized_new_run_id`) by phase, then lifts `evaluation_halted` alone. Release before the evaluator revisits that item: every visit rewrites the derived gate with a new `written_at_utc`, and the release needs the exact digest the receipt recorded. `research/arctic-eval-503-release-r1/report.md` holds the worked release.
- An ambiguous charge of a bounded case now releases itself and halts nothing, five times per phase per hour (`AUTOMATIC_CONTINUATION_LIMIT_PER_HOUR`). The record is the one the reviewed release writes, the whole reservation stays in `ambiguous_reserved_usd`, and nothing is settled, retried or replayed. Beyond the bound the charge halts its phase exactly as before. The bounded cases are four: an HTTP 5xx answer, a received response cut off at `MAX_TOKENS`, a provider timeout, and an interrupted orphan, whose receipt error is `interrupted request has no durable provider response` and which orphan recovery writes when the process that held a live call died.
- The release's custody precondition reads the phase whose halt it lifts. It did not before, so two unreviewed charges of different phases each blocked the other's release and neither halt could lift; that deadlock stopped both callers on 2026-09-17 at 10:24 UTC.
- An interrupted orphan of the evaluation phase may bind a later authorized successor of its derived gate, because the cut-over that interrupted the call rewrites that gate seconds later. The record carries both digests. No other case may do this, and the ledger row is never edited.
- A new receipt schema on the shared ledger is a cut-over of every reader, not a change to one writer. Every `ambiguous-continuation-*.json` of the receipts directory is read as an event by every caller, so a runtime that does not know a new schema refuses it and writes an integrity halt: that stopped the producer on 2026-09-17 at 10:30:48 UTC, minutes after the first such record. Ship the reader everywhere first, then write the record.
- The release, and every other exclusive broker operation, takes `.<ledger>.operation.lock` without a wait, and a live producer holds it for the whole of each paid call. A retry loop for that lock starved the chapter 3 producer into exiting on 2026-09-16 at 18:26 UTC. Run one such operation at a time and tell the supervisor the minute you run it.
- A Gemini vendor pause whose reason is an ambiguous charge lifts itself: `watch` reads `model_broker.phase_halt_reason` before every question it admits, through `resume_gemini_if_released`, and resumes the vendor after the release with a `vendor_resumed` event and a `vendor_resume` journal row. Every other vendor pause still needs a start.
Ask it at every admission, never only at the top of a poll cycle: one cycle scores four waves, and the arm stayed dark for the rest of one on 2026-09-17 after a pause at 11:31:26 UTC that the ledger had already released.
- A model of the evaluation plan can be paused without a stop of the run: `config/benchmark-evaluation-model-pause-v1.json`, re-read before every item, with an optional `resume_at_utc`. The "Paused models" section of `docs/ABSTENTION_EVALUATION.md` holds the contract. A control read in one place and consumed in another needs a test that drives the real path: the pause was dropped live on 2026-09-16 because the Gemini ceiling precheck reused its variable, and no scripted test passes a broker factory.
- The abstention prompt contract is `abstention-eval-prompt-v2`: the option order seed binds the model and the arm, so every call shuffles on its own (captain order 2026-09-16). The evaluation set id includes the prompt hash, so a contract change freezes a new set and a run refuses a set of another contract.
- The streaming evaluator scores several questions at once: `--item-workers`, 8 by default. Read "Several questions at once" in `docs/ABSTENTION_EVALUATION.md` before you change it. Four rules hold it: the pick-up order of the state database is given back to every reader, one admission is one critical section (the Gemini ceiling precheck keeps room for the questions in flight), a question in flight keeps the vendor list and the pause record it started with, and `watch-state.json` carries `items_in_flight` for the cost guard. The per-vendor slots are unchanged, because a slot belongs to the vendor: one question alone fills none of them, which is why 17 questions an hour became the bound at 08:35 UTC on 2026-09-17.
- A stop of the streaming evaluator that reserved nothing, submitted nothing and charged nothing belongs to one question, not to the arm: `abstention_watch.ITEM_SCOPED_REASONS` is the closed set (the per-item repeat limit, a busy exclusive operation lock, and `model_broker.TRANSIENT_RESERVATION_REASONS`, which are the full concurrency slots and the full minute window). A busy lock paused the whole Gemini arm at 09:58 UTC on 2026-09-17, and a full slot paused it at 11:55 UTC minutes after the arm got fast enough to fill one. A wave of questions meets all of them far more often than one question did.
A `BrokerOperationBusyError` never ends the watch, by whichever of its three routes it arrives: `evaluate_item` hands it back as text in `result["error"]`, which is the route it actually takes; `start_item` raises it from the Gemini ceiling read; and the frame around the plan raises it. `is_lock_busy_error` is the one predicate, each route emits `item_lock_busy`, and the final raise drops these lines whatever route they took. One such error per question of the wave exited the unit with status 1 at 12:14:20 UTC on 2026-09-17, and again at 12:49:45 UTC with only the frame contained.
- A vendor stop is read per pass, never from the run directory's history: `stopped_this_pass` in the vendor summary, not `stopped_on`. Nothing retries a stop, so a recorded stop names itself for ever, and a revisit is how a paused arm finishes the questions it owes. A pause reopens a question; an arm that stopped inside one does not, and such a question keeps its partial trials with the row-level `complete` flag false.

A later row holds the question's whole record, because the Gemini USD comes from the ledger and the outcomes from the run directory. The guard counted every row until 2026-09-17 and reported 128 questions where 78 had a row.

- The per-paper cost cap (`maximum_paper_cost_usd`) bounds one paper family, never the run. A refusal with `model_broker.PAPER_COST_CAP_REASON` reaches the producer as `errors.PaperCostCapError`; `streaming.py` records the family in `rejection_ledger` at stage `paper_cost_cap` with the reason code `paper_cost_cap_reached` and skips to the next paper. - Orphan recovery runs before every paid call and acts on a ledger snapshot, so a concurrent worker of the same shared ledger can settle one of those requests first. `_settle` therefore never raises for a row that is not `submitted`: it writes `<request_key>.settle-skipped.json` (`shared-paid-call-settle-skipped-v1`) and returns False. - An exception raised while one candidate or one paper family is built, routed, given options or persisted never ends the producer. `streaming._ends_the_run` names the only stops that do: a `BudgetError` (allocation ceiling, session ceiling, submission cap, accepted target), an `AmbiguousChargeError`, a stop signal, and any refusal `broker_provider.broker_boundary` marked at the seam. Wrap every new call into the shared broker in that boundary: it marks the execution gate, the ledger and every other broker refusal a run stop without a list of messages, and a missed one walks the whole corpus with a disabled gate. Everything else settles the family's `incomplete_infra` call records with the exception class, message and stage, writes a `generation_routing` row with reason code `candidate_processing_fault`, proves the broker holds no reservation for the family, and skips to the next paper. Three single-candidate faults ended three whole chapter 3 runs on 2026-09-16.
- The option repair rung has one closed trigger set with one owner: `generation.OPTION_REPAIR_TRIGGER_REASONS`, which `streaming.OPTION_REPAIR_REASONS` reads. Routing and the generation contract validate the same attempt, so a code in one set and not the other ends the producer; that split ended the run on 2026-09-16 at 16:28 UTC.
- `countTokens` is free, so a failure of it never makes money uncertain and must never halt the ledger on its own. A transient count failure (HTTP 429, 500, 502, 503, 504, a timeout, a connection fault, an unreadable count) is retried about two minutes, then becomes a `count_error` with `count_failure_class` `transient` that the producer contains against one family through `errors.CountUnavailableError`; a later visit counts the request again under a count-retry round. Only a permanent count failure (HTTP 400, 401, 403, 404, and anything unproven) halts. A 503 there halted the whole shared ledger and ended the chapter 3 producer on 2026-09-16 at 21:11 UTC. A stored transient count error is also never replayed as a result: `broker_provider.invoke` sends it back through `execute` for a new round, and a receipt older than the class field is read from its error string. Read "The free token count and its errors" in `docs/SHARED_MODEL_BROKER.md` before you widen the transient set or change the reviewed continuation evidence.
- The shared ledger has one exclusive operation lock, taken through `model_broker.hold_operation_lock`. Every reviewed operation (an authorization, a settlement, a reconciliation, an exclusive batch activation) takes it with no wait and refuses at once, because two reviewed operations of one ledger must never overlap. The one ordinary request path, `execute`, waits `OPERATION_LOCK_WAIT_SECONDS` for it instead and raises `errors.BrokerOperationBusyError` at the bound, which is a paper-level refusal: the family is skipped and the run continues. Do not give a new reviewed operation the wait, and do not make the bound-exceeded case a run stop; the immediate refusal ended the chapter 3 producer on 2026-09-16 at 18:26 UTC while another task held the lock. `tests/test_broker_operation_lock_wait.py` is the guard.
- A paper the chapter 3 producer finished carries a completion label in `paper_completions` of the state database, and the producer skips a labelled paper at startup before it reads one receipt of it. The rule is the "Paper completion labels" section of `docs/STREAMING_DATASET.md`; `paper_completion.classify_paper` owns it and the producer's own ladder `streaming._stored_generation_outcome` answers the generation half, so never write a second ladder. The table joins the schema under the current version because the evaluator's pinned snapshot refuses any other; never bump `SCHEMA_VERSION` for a table only a newer reader queries. The launcher names the commit with `--code-commit`: a runtime snapshot is a `git archive`, and `git rev-parse` inside it answers with the parent repository's commit.
- A relaunched chapter 3 producer replays the papers its eligibility run directory already holds before it makes its first paid call. That replay is free, CPU-bound and took about 20 minutes at 154 screened papers on 2026-09-16 (a labelled paper is skipped before its receipts are read, so it was under a minute on 2026-09-17), so a health window shorter than it sees a live producer, a moving `progress.json` and no ledger movement at all. Read `progress.json` `message`, the journal's size and the process CPU time before you call such a window unhealthy; the ledger file itself moves only on a compaction.
- Every paid-call request records its `phase` from its first ledger record, not from its reservation. An applied configuration transition is validated again on every broker start until its first construction request, and `_only_evaluation_activity_since` reads a row without a `phase` as construction. One phase-less evaluation refusal halted the whole shared ledger on 2026-09-16 at 23:03:56 UTC and stopped both the producer and the evaluator. `settle-phaseless-refusal` is the reviewed repair of one such row; read "The phase of a refused request" in `docs/SHARED_MODEL_BROKER.md`. While such a transition waits for its first construction request its validation also needs `inflight` to be 0, so a producer start and a live evaluator must not overlap until that first construction call lands.
- A paused vendor of the streaming evaluator owes its trials, exactly as a paused model does: the item is not complete and a later invocation runs only what is missing. `--vendors` is a scope, not a pause, and lands in `evaluation.vendors_excluded`. - A per-item plan manifest of the streaming evaluator binds the item's identity (plan, run id, evaluation set, arms, repeats, gate dir) and nothing else. The vendor set and `code_commits` grow, so a later pass, on a later snapshot, finishes an item's missing trials in the same work directory; each response row names the commit that ran it and a later pass writes `run-manifest-<commit>.json` beside the first. A new run id prefix still needs a new work directory. Read `abstention_plan.extend_plan_manifest`.
- A stop of the streaming evaluator lands at a trial boundary, never only between two whole items: `SIGTERM` sets a flag that `abstention_plan.run_vendor` reads before it dispatches each trial, and the trials it holds stay pending exactly as a paused model's do.
Give its unit a `TimeoutStopSec` longer than one trial of the slowest vendor; systemd killed it at the 90-second default on 2026-09-17 at 07:25:55 UTC, which left one free `counting` row and nothing else.
Read "Stopping the unit" in `docs/ABSTENTION_EVALUATION.md`.

- The producer runs several papers at once: `--paper-workers` papers in flight, `--option-workers` option verdicts inside one paper, both 4 by default and 1 for `--phase offline`. Read "Paper concurrency" in `docs/STREAMING_DATASET.md` and "Concurrent requests" in `docs/SHARED_MODEL_BROKER.md` before you change either half. Three rules hold the design: the frozen selection order is the pick-up order and `paper_results` is sorted back into it, the option rank-order stop holds at the wave boundary, and every request releases its admission and the exclusive operation lock before its live call so orphan recovery sees the in-flight lock instead. A scripted `FakeProvider` answers in script order, so any test that drives the concurrent path needs a provider matched by role and prompt markers (`tests/test_paper_concurrency.py`).
- The website section "Papers in analysis now" (`src/arctic_qa/live_papers.py`, `/api/live-papers`) derives the live picture from the shared ledger, the progress record and the state database, and writes to none of them. Read "Papers in analysis now" in `docs/CORPUS_VIEWER.md` before you change the derivation. A route that polls this page must not call `CorpusArtifacts.refresh`: a live producer moves the index fingerprint on every poll, and the rebuild took about 50 seconds on 2026-09-16.
- Under paper concurrency the exclusive operation lock is a queue, never a race: a concurrent construction request waits `OPERATION_LOCK_QUEUE_CEILING_SECONDS` over `OPERATION_LOCK_QUEUE_ROUNDS` rounds, a reached ceiling retries the same request key, and the lock holds the ledger mutation alone. Keep the free token count, its retries and the pacing wait outside it: holding them inside faulted 19 papers with `BrokerOperationBusyError` in 40 minutes on 2026-09-16. Every section prints its wait and its hold on stderr, which is how the lock is measured.
- The shared paid-call ledger is a store, not a file: the JSON file is the compacted snapshot, `.shared-paid-call-ledger.json.journal` beside it is the append-only journal, and the base record binds the two. Never `json.load` the file to read the ledger; read it with `ledger_store.read_ledger`, and never write the file by hand (a snapshot changed outside the store fails closed; a test rewrites one with `tests/test_model_broker.py::rewrite_ledger`). A broker on a ledger with no store refuses and names `migrate-ledger-store`. The file moves only on a compaction, so its mtime is not a sign of life; the journal's is. Read "Parallel bookkeeping" in `docs/SHARED_MODEL_BROKER.md` and `research/arctic-ledger-parallel-r1/report.md` before you change the store, the compactor or a reader.
- A tracked ledger container rolls itself back and is never replaced by a copy of what it held, and a parent keeps a reference to a tracked child and never a copy.
The replacement untracked the map, so every later change to it went unreported and the next read raised, which writes an integrity halt on the shared ledger; the copy cost 90 ms of every commit at 8,631 rows.

Read "A mutation that was never committed" in `docs/SHARED_MODEL_BROKER.md`; `tests/test_ledger_store.py` is the guard.
- The chapter 3 construction allocation is USD 600 on top of the USD 53.990121 spent before the run, so the away ceiling and the construction review checkpoint are both USD 653.990121 and move only together (`CHAPTER3_SIX_HUNDRED_CHANGE`, captain order 2026-09-17 08:25 UTC).

- The paper thread count has a knee at about 32, and the knee is the interpreter, not the ledger and not Google. Nobody waits for the exclusive lock any more (mean wait one millisecond); what grows with the thread count is the hold, because the holder shares one interpreter with every other paper thread: 0.206 s a call at 32 threads, 0.319 s at 50, for the same 26 ms of real work.
The number in flight settles at the call length over that hold. More papers in flight past the knee buys breadth and pays in request rate, and 100 threads in one process would be slower than 50. Read `research/arctic-ch3-concurrency-50-r1/report.md` before you raise it again; the next step is producer processes over disjoint halves of the Jev ranking, and the full immutable-event pass off the hot path.
- Nothing on the paid-call path may cost the whole history. The immutable-event proof did: one warm read cost 371 ms at 8,230 rows and 32,251 receipts, which held the exclusive operation lock a mean 2.4 s a call and held the run at 21 requests a minute whatever the thread count was.
The receipts directory is listed once (`RECEIPT_LISTING_REFRESH_SECONDS` on the concurrent path), everything read out of a listing is derived once (`_listing_derived`), no glob of that directory is on the call path, and a row is proved again only when the store reports it moved.
A receipt the broker writes together with the ledger row that names it is never proved from a stale listing: the accepted-item proof lists the directory again and is keyed on the ledger's own accepted map, because caching it against the listing raised a false integrity halt at 07:40:51 UTC on 2026-09-17 and stopped the producer.
Read "The immutable-event proof, and what one read of it costs" in `docs/SHARED_MODEL_BROKER.md` and `research/arctic-ch3-concurrency-50-r1/report.md`; `tests/test_ledger_proof_cost.py` is the guard.
- Every arm of the streaming evaluator gets a share of every wave of questions: `abstention_watch.wave_order`, over what `CostJournal.open_vendors_by_item` says each question still owes. The pick-up order alone is the oldest question first, and a paused arm leaves its held questions at the front, so the captain's Claude pause of 2026-09-17 filled all eight slots with Claude-only questions and the Gemini arm made no paid call between 10:03 and 11:06 UTC while 23 questions owed it trials.
Read "Every arm gets a share of the wave" in `docs/ABSTENTION_EVALUATION.md`; `tests/test_abstention_watch.py` is the guard.
- A second broker of one shared ledger in one process starts from what that process already proved: `model_broker._seed_ledger_proof`, published by `_publish_ledger_proof` at the end of every immutable-event pass. The evaluator builds one broker a question, and that start proved every row against its receipts and stated the final receipt of every terminal row: 2.6 s and 0.24 s at 15,347 rows, under the shared ledger lock, which took the exclusive sections past the bounded wait and lost every question of a wave to `BrokerOperationBusyError` at 12:13 UTC on 2026-09-17.
A seeded start is not a pass: it still takes the signature of every row and re-proves the ones that moved, and the full pass every `IMMUTABLE_EVENT_REVALIDATION_SECONDS` still clears the custody set. `tests/test_ledger_proof_cost.py` is the guard.
- The streaming evaluator is the shared ledger's second live writer, and it says so with `concurrent_requests`: a broker parameter, never an attribute a caller sets afterwards, because the start of the broker reads it. `concurrent_construction` still implies it.
Without it the evaluator kept the exact receipts fingerprint that the producer moves on every paid call, so every one of its ledger reads was a full listing of 52,716 entries: 0.25 s a read against 0.026 s kept.
Its broker per question also started the whole ledger again each time, which is a 60 MB materialization, a proof of every row and an 18 MB durable write under the shared ledger lock, and left a compactor thread behind. One process now starts one ledger once and runs one compactor thread for it.
Read "The immutable-event proof, and what one read of it costs" and "One process starts one ledger once" in `docs/SHARED_MODEL_BROKER.md`; `tests/test_ledger_proof_cost.py` is the guard.
- Every opener of the state database goes through `db.connect_read_only` or `db.Database`, which carry `db.BUSY_TIMEOUT_SECONDS`; the database runs in WAL mode (switched live at 05:23 UTC on 2026-09-17, set by `Database.__init__` for a fresh one), and a locked read is a retry through `db.retry_locked_read`, never an exit. The streaming evaluator exited on `database is locked` under sixteen producer threads with the five-second default.
- The cost of a paid call is ledger work, not the model, and on this data disk (a USB rotating disk) a durable write costs 150 to 470 ms whatever its size. The store makes one call cost its own change: one appended record, one shared `fsync`, a proof of the rows that moved. `_validate_immutable_events` costs the rows that moved and the receipts that arrived, never the history, with a full pass on construction and every `IMMUTABLE_EVENT_REVALIDATION_SECONDS`. The shared ledger lock is shared with the benchmark evaluator, which must run the same store code: an evaluator on the one-file code would rewrite the snapshot whole.
- A refusal of the broker that reserves nothing and charges nothing is a paper-level error, never a plain `ValueError`: `broker_provider.broker_boundary` marks every other exception a run stop. `DuplicateRequestKeyError` (02:32 UTC) and `PaperBindingConflictError` (05:25 UTC, the family, paper and source-version binding checks of `_count_event`) both ended the producer on 2026-09-17 as plain `ValueError`s first. A new refusal joins `_PAPER_LEVEL_BROKER_ERRORS` and the non-stop set of `streaming._ends_the_run`, with a test.
- A `counting` ledger row is a free count that never reached a reservation: nothing reserved, submitted or charged. A stop between the two leaves one, and the next start meets its own key. `_reusable_counting_row` reuses such a row when the request identity matches and adds no row count; every other existing key raises `errors.DuplicateRequestKeyError`, which is a paper-level refusal, never a run stop. A plain `ValueError` there ended the producer on 2026-09-17 at 02:32 UTC.
- A paper's completion time is recorded in three places and read back by the website: `state_changed_at_utc` on the producer's progress row, `completed_at_utc` on the `paper_completions` label, and `pipeline_trace`, which falls back to the label and never replaces a known time with nothing. `arctic-qa repair-concurrency-faults` clears the papers an operation-lock refusal recorded and backfills a missing date.
- Not every row in the `candidates` table is a benchmark item. A row whose status is in `streaming.INCOMPLETE_CANDIDATE_STATUSES` records one generation call. Query benchmark items with `streaming.BENCHMARK_CANDIDATE_PREDICATE`.
