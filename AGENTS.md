# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- `README.md` maps the repository, `docs/README.md` indexes the documentation by task, and `docs/REPRODUCTION.md` is the path from a clean checkout to a free end-to-end run. Keep all three current when you add a document or a top-level directory.
- The data root and the credential directory are configuration, not constants: `ARCTIC_QA_DATA_ROOT` and `ARCTIC_QA_CONFIG_DIR`, resolved in `src/arctic_qa/paths.py`. The tests take `ARCTIC_CH2_EVIDENCE_DIR`, `ARCTIC_REAL_CORPUS_DIR`, `ARCTIC_REAL_CORPUS_RUN` and `ARCTIC_ZOTERO_RECEIPTS_DIR`. Never hard-code an absolute path of one machine in `src/` or `tests/`; give it an environment variable whose default keeps the current value.
- Task reports and their measurement files go under `research/<task>/`, never `data/`, and `research/README.md` needs a row for each new directory. The reports keep their historical absolute paths, because they are records.
- Read `docs/CORPUS_VIEWER.md` before you operate the read-only corpus-stage monitor.
- Read `docs/PUBLICATION_EXPORT.md` before you operate the live publication snapshot service.
- Read `docs/SOURCE_SCREENING_PASS.md` before you operate a bounded source pass.
- Read `docs/BENCHMARK_GUARD.md` before you operate the benchmark cost and quota guard or the "Live benchmarking" section of the viewer. The guard pauses one model through the `benchmark-evaluation-model-pause-v1` file and never by stopping a process; it removes only the entries it owns. Its own cross-cycle state lives in `guard-memory.json` in the guard dir: the Codex attribution samples and the pause hysteresis. Never put guard state in the pause file, and never copy a guard dir between runs of different journals. A shared quota window with no per-caller attribution needs a measured share before a rule pauses on it: the Codex projection rule flapped on 2026-09-16 because "the evaluator booked one more call" was taken as proof that the benchmark drove the window.
- Read `docs/ABSTENTION_EVALUATION.md` before you build, dry-run, or run the abstention evaluation. A paid run needs a reviewed private evaluation gate and the construction files that the production ledger already binds; the dry run needs neither.
- A subscription evaluation run (Claude Code, Codex) needs the harness login, a reviewed gate with `--provider`, and a subscription ledger directory. Do not change the Codex config in `abstention_subscription.py` without a captured request: `tools.web_search = false` does not remove web search, only `web_search = "disabled"` does. The evaluation gate binds `config/benchmark-evaluation-subscription-models-v1.json` by hash in the price-config slot, so its absolute binary paths stay as they are; another machine passes `--binary-path` or its own registry file.
- A provider can omit either zero token count. gemini-3.7-flash omitted `candidatesTokenCount` once in three calls on 2026-09-16 and halted the shared ledger. `_omitted_zero_usage_field` accepts both shapes, and `reconcile_omitted_thought_usage` settles either from the saved response. Read section 7 of `research/arctic-abstention-streaming-eval-r1/report.md` before the large Gemini run.
- A usage record missing BOTH token counts must keep raising `provider usage cannot prove zero thinking tokens`. The reviewed chapter 2 continuation of the `answer_agreement` MAX_TOKENS incident matches receipts by that exact string, so a changed message breaks a money-settlement path. `tests/test_ambiguous_continuation.py` is the guard.
- The evaluator's paused-model switch is a documented interface that the benchmark cost guard calls: the `benchmark-evaluation-model-pause-v1` file, the repeatable `--pause-file`, and `--action pause-status`. `docs/BENCHMARK_GUARD.md` holds the guard's half. A paused model's trials stay pending, so read a run's totals through `CostJournal.latest_item_rows`.
- An ambiguous `benchmark_evaluation` request halts the evaluation phase only, through `evaluation_halted` in the ledger. Construction continues under its own ceiling. Never widen that halt back to the whole ledger: one evaluation error stopped the live chapter 3 producer on 2026-09-16.
- Release that charge under its own derived per-item evaluation gate, never the construction gate: `authorize-ambiguous-continuation` takes the evaluation trio and picks the gate and the run-id field (`authorized_run_id`, not `authorized_new_run_id`) by phase, then lifts `evaluation_halted` alone. Release before the evaluator revisits that item: every visit rewrites the derived gate with a new `written_at_utc`, and the release needs the exact digest the receipt recorded. `research/arctic-eval-503-release-r1/report.md` holds the worked release.
- The release, and every other exclusive broker operation, takes `.<ledger>.operation.lock` without a wait, and a live producer holds it for the whole of each paid call. A retry loop for that lock starved the chapter 3 producer into exiting on 2026-09-16 at 18:26 UTC. Run one such operation at a time and tell the supervisor the minute you run it.
- A Gemini vendor pause whose reason is an ambiguous charge lifts itself: `watch` reads `model_broker.phase_halt_reason` on every poll and resumes the vendor after the release, with a `vendor_resumed` event and a `vendor_resume` journal row. Every other vendor pause still needs a start.
- A model of the evaluation plan can be paused without a stop of the run: `config/benchmark-evaluation-model-pause-v1.json`, re-read before every item, with an optional `resume_at_utc`. The "Paused models" section of `docs/ABSTENTION_EVALUATION.md` holds the contract. A control read in one place and consumed in another needs a test that drives the real path: the pause was dropped live on 2026-09-16 because the Gemini ceiling precheck reused its variable, and no scripted test passes a broker factory.
- The abstention prompt contract is `abstention-eval-prompt-v2`: the option order seed binds the model and the arm, so every call shuffles on its own (captain order 2026-09-16). The evaluation set id includes the prompt hash, so a contract change freezes a new set and a run refuses a set of another contract.
- The concurrent plan (`abstention-eval --action run-plan`) and the streaming evaluator (`--action watch`) run the whole 8-model plan per question. Read the "Concurrent plan" and "Streaming evaluator" sections of `docs/ABSTENTION_EVALUATION.md` before you change the evaluation concurrency, the derived gates or the cost journal. The evaluation phase of the shared ledger keeps its own concurrency slots, its own minute window and an in-flight lock per request; an evaluation admission recovers only its own run, because a construction run of another run id can be inside a live call.
- Read `docs/STANDALONE_CALIBRATION.md` before you change `STANDALONE_SYSTEM` or record a standalone calibration cassette. Recording is a paid call; replay is free.
- Run the tests as `nix develop -c bash -c 'PYTHONPATH=src pytest tests/ -q'`. The package is not installed in the devshell, so pytest cannot import `arctic_qa` without `PYTHONPATH=src`.
- A whole-suite run takes about 20 minutes. `tests/test_model_broker.py` and `tests/test_streaming.py` hold real rate-limit sleeps.
- Read `docs/CHAPTER2_CORPUS.md` before you extract, freeze, or read the chapter 2 corpus.
- Read the "Chapter 3 call plan" section of `docs/STREAMING_DATASET.md` before you change the order of the paid calls in `generate_candidate`, the finding bank, or the option call plan.
- `config/gemini-eligibility-v1.json` is bound into every paid receipt through `price_config_sha256`. Any edit to it needs a chained ledger price transition before a live run can resume, and a new `config_id` revision rather than a changed meaning for an old one.
- No change to `STANDALONE_SYSTEM` ships without a live calibration run on the judge model (paid, captain-approved). The fixture rows live in `fixtures/standalone-calibration-*.jsonl`; the header of each file states its slice and release rule.
- One paper can hold three eligibility job rows in a run directory: the first screening, one bounded format re-ask, and one bounded geography re-screen. Each row binds its own broker receipt. `streaming.py::_load_eligibility_jobs` takes the last attempt, and `_attempt_order` defines that order.
- The activity-span dimension label is a span filter, never a paper-ending error. `_dimension_supported` drops the span it refuses and records it in `dimension_span_filter`; a span that is not Latin script is forwarded with `dimension_verified: false`, because every marker word is English. Widen `_DIMENSION_MARKERS` only against span text a run recorded.
- A geography re-screen answer carries all five criteria rows, because schema v4 sets `minItems` and `maxItems` of `criteria` to 5. `validate_response` reads only `study_geography` from it and takes the other four statuses from the re-screen note (`_frozen_rescreen_statuses`). Do not ask the model to omit them.
- The provider rejects an `enum` inside the `items` of an array in a response schema (HTTP 400 `INVALID_ARGUMENT`, 2026-09-16). `tests/test_eligibility_request_constraints.py` keeps every live eligibility schema inside the accepted keyword set. A rejection before generation is settled with `settle-http-rejection` (`docs/SHARED_MODEL_BROKER.md`, "Provider rejections"); the broker keeps the provider error body of every non-2xx answer in the receipt.
- The stream's invocation manifest is immutable per run id and binds the eligibility prompt and schema hashes; a corrected input needs a new run id on the same campaign.
- The broker accepts only registered budget transitions: a new construction ceiling needs its constant in `CEILING_CHANGES` and in `_validate_policy` of `src/arctic_qa/model_broker.py` before a transition file can apply (`tests/test_chapter3_production_run.py` shows the chain). A change set may move several policy fields at once (`CHAPTER3_EXPANSION_CHANGE`); every exact value `_validate_policy` pins, such as the submission count, the accepted target and the review checkpoint, ends a run before the ceiling does unless it moves with it. The construction baseline is the ledger's `spent_usd` minus the evaluation-stage spend.
- A live standalone calibration recording runs through the production gate and binds its streaming input; `docs/STANDALONE_CALIBRATION.md` gives the command.
- The broker's concurrency slots are per phase (`_phase_inflight` in `model_broker.py`); the per-minute window stays shared. A `not_submitted` receipt with a concurrency or minute reason is a stale refusal, not a budget stop: `execute` waits for room first, and the next reviewed transition resumes the request (`tests/test_phase_scoped_slots.py`).
- The per-paper cost cap (`maximum_paper_cost_usd`) bounds one paper family, never the run. A refusal with `model_broker.PAPER_COST_CAP_REASON` reaches the producer as `errors.PaperCostCapError`; `streaming.py` records the family in `rejection_ledger` at stage `paper_cost_cap` with the reason code `paper_cost_cap_reached` and skips to the next paper. Only an allocation ceiling, a session ceiling or a halt ends the producer. The refused receipt is immutable and is not in `RESUMABLE_NOT_SUBMITTED_REASONS`, so a relaunch replays it free and never re-tries the capped family.
- Orphan recovery runs before every paid call and acts on a ledger snapshot, so a concurrent worker of the same shared ledger can settle one of those requests first. `_settle` therefore never raises for a row that is not `submitted`: it writes `<request_key>.settle-skipped.json` (`shared-paid-call-settle-skipped-v1`) and returns False. A double settlement ended the chapter 3 producer on 2026-09-16 at 13:53 UTC. Read "Orphan recovery and concurrent settlement" in `docs/SHARED_MODEL_BROKER.md` before you change the recovery or the settlement.
- An exception raised while one candidate or one paper family is built, routed, given options or persisted never ends the producer. `streaming._ends_the_run` names the only stops that do: a `BudgetError` (allocation ceiling, session ceiling, submission cap, accepted target), an `AmbiguousChargeError`, a stop signal, and any refusal `broker_provider.broker_boundary` marked at the seam. Wrap every new call into the shared broker in that boundary: it marks the execution gate, the ledger and every other broker refusal a run stop without a list of messages, and a missed one walks the whole corpus with a disabled gate. Everything else settles the family's `incomplete_infra` call records with the exception class, message and stage, writes a `generation_routing` row with reason code `candidate_processing_fault`, proves the broker holds no reservation for the family, and skips to the next paper. Three single-candidate faults ended three whole chapter 3 runs on 2026-09-16.
- The option repair rung has one closed trigger set with one owner: `generation.OPTION_REPAIR_TRIGGER_REASONS`, which `streaming.OPTION_REPAIR_REASONS` reads. Routing and the generation contract validate the same attempt, so a code in one set and not the other ends the producer; that split ended the run on 2026-09-16 at 16:28 UTC.
- `countTokens` is free, so a failure of it never makes money uncertain and must never halt the ledger on its own. A transient count failure (HTTP 429, 500, 502, 503, 504, a timeout, a connection fault, an unreadable count) is retried about two minutes, then becomes a `count_error` with `count_failure_class` `transient` that the producer contains against one family through `errors.CountUnavailableError`; a later visit counts the request again under a count-retry round. Only a permanent count failure (HTTP 400, 401, 403, 404, and anything unproven) halts. A 503 there halted the whole shared ledger and ended the chapter 3 producer on 2026-09-16 at 21:11 UTC. A stored transient count error is also never replayed as a result: `broker_provider.invoke` sends it back through `execute` for a new round, and a receipt older than the class field is read from its error string. Read "The free token count and its errors" in `docs/SHARED_MODEL_BROKER.md` before you widen the transient set or change the reviewed continuation evidence.
- The shared ledger has one exclusive operation lock, taken through `model_broker.hold_operation_lock`. Every reviewed operation (an authorization, a settlement, a reconciliation, an exclusive batch activation) takes it with no wait and refuses at once, because two reviewed operations of one ledger must never overlap. The one ordinary request path, `execute`, waits `OPERATION_LOCK_WAIT_SECONDS` for it instead and raises `errors.BrokerOperationBusyError` at the bound, which is a paper-level refusal: the family is skipped and the run continues. Do not give a new reviewed operation the wait, and do not make the bound-exceeded case a run stop; the immediate refusal ended the chapter 3 producer on 2026-09-16 at 18:26 UTC while another task held the lock. `tests/test_broker_operation_lock_wait.py` is the guard.
- A relaunched chapter 3 producer replays the papers its eligibility run directory already holds before it makes its first paid call. That replay is free, CPU-bound and took about 20 minutes at 154 screened papers on 2026-09-16, so a health window shorter than it sees a live producer, a moving `progress.json` and no ledger movement at all. Read `progress.json` `message` and the process CPU time before you call such a window unhealthy.
- Every paid-call request records its `phase` from its first ledger record, not from its reservation. An applied configuration transition is validated again on every broker start until its first construction request, and `_only_evaluation_activity_since` reads a row without a `phase` as construction. One phase-less evaluation refusal halted the whole shared ledger on 2026-09-16 at 23:03:56 UTC and stopped both the producer and the evaluator. `settle-phaseless-refusal` is the reviewed repair of one such row; read "The phase of a refused request" in `docs/SHARED_MODEL_BROKER.md`. While such a transition waits for its first construction request its validation also needs `inflight` to be 0, so a producer start and a live evaluator must not overlap until that first construction call lands.
- A paused vendor of the streaming evaluator owes its trials, exactly as a paused model does: the item is not complete and a later invocation runs only what is missing. `--vendors` is a scope, not a pause, and lands in `evaluation.vendors_excluded`. Before 2026-09-17 a paused vendor did not stop an item being complete, and two items were recorded complete with 30 of their 48 trials when the Claude Code binary vanished for a moment during a package upgrade. `CostJournal.row_is_complete` applies the rule to old rows too, so such an item re-opens without an edit of the journal.
- A bound that stops the streaming evaluator is not an error, so it exits 0 and says nothing: the unit met its item bound at 2026-09-16T19:31:44Z and nobody saw it until the next morning. Give `watch` a `--status-file`, and read the cost guard's own report of an evaluator that stopped polling ("The evaluator itself" in `docs/BENCHMARK_GUARD.md`).
- The producer runs several papers at once: `--paper-workers` papers in flight, `--option-workers` option verdicts inside one paper, both 4 by default and 1 for `--phase offline`. Read "Paper concurrency" in `docs/STREAMING_DATASET.md` and "Concurrent requests" in `docs/SHARED_MODEL_BROKER.md` before you change either half. Three rules hold the design: the frozen selection order is the pick-up order and `paper_results` is sorted back into it, the option rank-order stop holds at the wave boundary, and every request releases its admission and the exclusive operation lock before its live call so orphan recovery sees the in-flight lock instead. A scripted `FakeProvider` answers in script order, so any test that drives the concurrent path needs a provider matched by role and prompt markers (`tests/test_paper_concurrency.py`).
- Not every row in the `candidates` table is a benchmark item. A row whose status is in `streaming.INCOMPLETE_CANDIDATE_STATUSES` records one generation call. Query benchmark items with `streaming.BENCHMARK_CANDIDATE_PREDICATE`.
